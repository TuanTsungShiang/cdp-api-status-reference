核心設計原則

我們不是為了讓 Status Code「更漂亮」而重構，而是要縮短從 Error 發生 → 理解 → 定位 → 行動的時間。

1發生什麼？
2是哪一類問題？
3具體原因在哪裡？
4是哪一次 Request / Job？
5下一步該做什麼？
01 · Adobe Experience Platform / Real-Time CDP

結構完整：Status + Code + Human Message + Source + Trace

HTTP/1.1 404 Not Found
Content-Type: application/json

{
  "errors": [
    {
      "id": "8a5526da-ab12-4be9-b084-2efe537f388c",
      "status": "404",
      "code": "not-found",
      "title": "Record Not Found",
      "meta": {
        "request_id": "jfb0dQ2e0XVTkQ6AOfEJFfTDjguw9x3d"
      },
      "source": {
        "pointer": "/data"
      }
    }
  ]
}
欄位角色
statusHTTP 問題分類
codeApplication Error Code
title / detail人類可直接理解
source.pointer指出 Request 中的問題位置
id / request_idTrace / Log 追蹤
啟示： 問題分類 → 語意 → 問題位置 → Trace，一個 Response 即可完成大部分判斷。
02 · Salesforce Data 360

CDP 特別重要：HTTP 成功，不代表後續資料處理一定成功

Bulk Operation Error

[
  {
    "statusCode": 400,
    "result": [
      {
        "errorCode": "INVALID_INPUT",
        "message": "Invalid developer name format"
      }
    ]
  }
]
[
  {
    "statusCode": 404,
    "result": [
      {
        "errorCode": "RESOURCE_NOT_FOUND",
        "message": "Tag taxonomy 'Unused_Tags' not found"
      }
    ]
  }
]

Data Stream Job Response Schema

{
  "errors": [
    {
      "errorCode": "string",
      "errorMessage": "string"
    }
  ],
  "success": true,
  "jobId": "string"
}
Request → Accepted → Queue → Processing → Transformation → Identity Resolution → Activation
啟示： CDP 要區分 HTTP Request、Business Processing、Job、單筆資料等不同層級的 Status。
03 · Oracle Unity Customer Data Platform

直白：HTTP Status + 具體 Error Message

HTTP/1.1 422 Unprocessable Entity

{
  "errorMessage": "Invalid UTF-8 start byte 0x80\n at [Source: (); line: 7, column: 32] (line 7, column 13)",
  "httpstatus": "422"
}

另一個 Validation Error：

{
  "errorMessage": "Illegal input: tableDeleteOptions.truncateOptions.objects contains an object that doesn't exist: crustomer",
  "httpstatus": "422"
}
啟示： 「簡單」不是字數少，而是看到 Response 後不需要額外翻譯。
04 · SAP Customer Data Platform

分工清楚：StatusCode + ErrorCode + ErrorMessage

成功

{
  "ErrorCode": 0,
  "StatusCode": 200,
  "SetHttpStatus": false
}

Customer Not Found

{
  "ErrorCode": 404000,
  "ErrorMessage": "Not found",
  "StatusCode": 404,
  "SetHttpStatus": false
}

Internal Server Error

{
  "ErrorCode": 500000,
  "ErrorMessage": "Internal Server Error",
  "StatusCode": 500,
  "SetHttpStatus": false
}
啟示： SAP 已把大分類、程式識別、人類閱讀分開；若我們從零設計，可讓 Application Code 本身更語意化，例如 CUSTOMER_NOT_FOUND。
05 · Tealium Customer Data Hub / AudienceStream

Body 可以空，但 Trace ID 不能缺

HTTP/1.1 400 Bad Request
Content-Type: application/json
X-Error: Missing required tealium_account or tealium_profile param value
X-Region: us-east-1
X-ServerID: uconnect_i-9a157d19
X-UUID: d4fc78d1-8204-412c-a6cb-57869d2370a7
Content-Length: 0
400 → Client Request 有問題 X-Error → 缺少必要參數 X-UUID → 唯一 Request 識別 X-Region / X-ServerID → 快速定位處理環境
啟示： Client 回報問題時，只要給一個唯一 ID，就能大幅降低雙方重新描述與搜尋 Log 的成本。

建議的 CDP Error Response

HTTP/1.1 422 Unprocessable Content

{
  "success": false,
  "code": "SCHEMA_VALIDATION_FAILED",
  "message": "The submitted data contains invalid fields.",
  "errors": [
    {
      "field": "email",
      "code": "INVALID_EMAIL_FORMAT",
      "message": "Email format is invalid."
    }
  ],
  "request_id": "req_01KABC123"
}
欄位責任
HTTP StatusProtocol 層 / 問題大方向
code穩定、可被程式判斷的 Error Type
message給人閱讀
errors / details欄位或細節
request_idLog / Trace / 問題回報入口
Error Code 的目標不是節省字元，而是節省人的判斷時間。

因此我們追求的不是「最短的 Code」，而是最短的判斷路徑。
