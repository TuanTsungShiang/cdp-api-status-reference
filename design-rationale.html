CDP API Design / Error Handling

CDP API Status Code 重構的思考邏輯

從現況問題、核心根因、設計原則到成功判準，整理出一套以「降低判斷與處理時間」為核心的 API Error Design 邏輯。

CDP API Status Code 重構的思考邏輯

一、問題的起點

這次會想重新設計 API 的 Status / Error Code，起點其實很單純：

我們自己在串接與測試 API 的過程中，發現現有的 Status Code 存在一些不一致、不直覺，甚至不符合實際錯誤情境的情況。

表面上看起來，問題是：

Code 設計得不夠好。

但往下追一層，真正造成困擾的其實不是 Code 長得不好看，而是：

當我們看到這些 Code 時，沒有辦法立刻知道發生了什麼事情。

二、真正的核心問題：判斷成本太高

每次發生錯誤時，我們現在往往需要額外經過一段判斷流程：

看到 Code
→ 思考它代表什麼
→ 查文件或程式
→ 確認實際錯誤原因
→ 判斷問題出在 Client 還是 Server
→ 再決定接下來要怎麼處理

這段額外的判斷流程，就是目前真正產生時間成本的地方。

而且這個問題不只發生在我們內部。

對 Client 端來說也是一樣。

如果錯誤資訊不夠清楚，Client 無法直接判斷問題，就必須再回頭詢問我們；我們收到問題後，又需要重新確認當時的 Request、Log、輸入資料與錯誤情境。

最後就會形成：

Client 無法判斷
→ 回報我們
→ 我們重新確認問題
→ 雙方來回溝通
→ 才找到真正原因

因此真正要解決的問題，其實不是單純「重新編一套 Status Code」。

我們真正想改善的是：

降低問題發生之後，雙方理解、判斷、定位與處理問題所需要的時間。

三、這次重構的核心目標

新的 API Error Design，核心不是追求：

  • Code 更短
  • Code 更整齊
  • 編號更一致
  • 看起來更像一套規範

真正的核心目標是：

讓使用者在看到錯誤 Response 的當下，就能更快知道發生了什麼事情，以及下一步要怎麼處理。

換句話說：

Error Code 的目標不是節省字元，而是節省人的判斷時間。

四、設計原則

1. 錯誤資訊要簡單、直白

例如，與其使用：

M002

不如直接使用：

MEMBER_NOT_FOUND

因為 M002 雖然比較短，但使用者還需要再經過一次查詢與翻譯：

看到 M002
→ 查文件
→ 找到 M002
→ 讀取定義
→ 才知道會員不存在

而 MEMBER_NOT_FOUND 幾乎可以直接理解。

因此我們所追求的「簡單」不是字數越少越好，而是：

理解成本越低越好。

2. HTTP Status 與 Application Error Code 各自負責不同層級

HTTP Status Code 應該遵循標準語意，例如：

400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content
429 Too Many Requests
500 Internal Server Error
503 Service Unavailable

而 Application Error Code 則負責表達具體的業務或系統錯誤，例如：

MEMBER_NOT_FOUND
INVALID_ACCESS_TOKEN
SCHEMA_VALIDATION_FAILED
IDENTITY_CONFLICT
RATE_LIMIT_EXCEEDED
DESTINATION_UNAVAILABLE
INTERNAL_ERROR

可以理解為：

HTTP Status
→ 告訴使用者大方向發生了什麼

Application Error Code
→ 告訴使用者具體是哪一類問題

3. Code 告訴問題類型，Message 補充細節

例如：

{
  "code": "SCHEMA_VALIDATION_FAILED",
  "message": "The submitted event contains invalid data."
}

code 應該是穩定、可讓程式判斷的值。

message 則是給人閱讀，用來補充錯誤內容。

如果還有更細的欄位錯誤，可以另外放進 errors 或 details：

{
  "code": "SCHEMA_VALIDATION_FAILED",
  "message": "The submitted event contains invalid data.",
  "errors": [
    {
      "field": "email",
      "code": "INVALID_EMAIL_FORMAT",
      "message": "Email format is invalid."
    }
  ]
}

這樣就不需要把所有資訊全部塞進一段 message。

4. 每次 Request 都應該可以被追蹤

錯誤發生時，其中一個最浪費時間的地方，就是無法快速找到對應的 Log。

因此每一次 API Request 最好都提供唯一的：

request_id

或：

trace_id

例如：

{
  "success": false,
  "code": "SCHEMA_VALIDATION_FAILED",
  "message": "The submitted event contains invalid data.",
  "request_id": "req_01KABC123"
}

當 Client 回報問題時，不需要描述：

昨天晚上某個會員送了一筆資料，好像有失敗。

只需要提供：

request_id = req_01KABC123

我們就可以直接從 Log 反查：

Request
→ Input
→ Validation
→ Processing
→ Error

這可以大幅降低雙方重新確認資訊的時間。

5. Error Response 最好能幫助使用者判斷下一步

好的 Error Code 不只是描述發生了什麼，也應該幫助使用者判斷接下來要怎麼做。

例如：

INVALID_ACCESS_TOKEN
→ 重新取得或更新 Token
SCHEMA_VALIDATION_FAILED
→ 修改輸入資料
RATE_LIMIT_EXCEEDED
→ 不需要修改資料，稍後 Retry
DESTINATION_UNAVAILABLE
→ 下游服務暫時不可用，可以考慮 Retry
INTERNAL_ERROR
→ 問題可能需要由 Server Side 進一步處理

因此 Error Code 本質上不只是錯誤名稱，也可以視為一個：

Decision Signal

它是在告訴使用者、程式、SDK、Queue Worker 或 Monitoring System：

接下來該怎麼做。

五、建議的 Response 結構

例如：

422 Unprocessable Content
{
  "success": false,
  "code": "SCHEMA_VALIDATION_FAILED",
  "message": "The submitted event contains invalid data.",
  "errors": [
    {
      "field": "email",
      "code": "INVALID_EMAIL_FORMAT",
      "message": "Email format is invalid."
    }
  ],
  "request_id": "req_01KABC123"
}

這筆 Response 可以讓使用者快速完成判斷：

422
↓
Schema 驗證失敗
↓
email 有問題
↓
email 格式錯誤
↓
應修改資料，而不是直接重送
↓
如果仍有問題，可以提供 request_id 讓 Server Side 查 Log

六、這套設計真正降低的是什麼成本

好的 Error Design 不只改善工程師的開發體驗。

它同時降低：

Client 工程師除錯時間
+
Server 工程師查 Log 時間
+
雙方溝通時間
+
客服 / PM 轉述問題的成本
+
來回確認次數
+
問題平均處理時間

因此這次 Status Code 重構，本質上是在改善整個問題處理流程的效率。

七、因果邏輯總結

整體的因果鏈可以整理成：

現有 Status / Error Code 不一致、不直覺
↓
看到錯誤後無法立即理解
↓
需要額外查詢、思考、判斷
↓
增加 Client 與 Server 雙方的時間成本
↓
問題回報時還需要重新確認大量資訊
↓
問題處理速度變慢
↓
因此需要重新設計 Error Handling
↓
使用直白、穩定、具語意的 Error Code
↓
搭配清楚的 Message / Errors
↓
加入唯一的 request_id / trace_id
↓
讓使用者快速理解、定位並決定下一步
↓
降低整體判斷、溝通與除錯成本

八、最終設計理念

這次重構的核心設計理念可以總結為：

以降低問題判斷與處理時間為首要目標。錯誤資訊應簡單、直白、具可操作性，讓使用者能快速理解發生了什麼事情；同時透過唯一的 Request ID 建立可追蹤性，降低 Client 與 Server 雙方的除錯、溝通與問題定位成本。

換句話說：

我們不是為了讓 Status Code 更漂亮而重構，而是因為現在的 Status Code 增加了人的判斷成本，所以才需要重新設計。

而新的設計是否成功，也不應該只用：

Code 有沒有統一格式

來衡量。

真正應該看的指標是：

發生問題之後，我們能不能比以前更快知道問題在哪裡，並且更快解決它。
